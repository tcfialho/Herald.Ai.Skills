# Reflective refinement

Improve the user’s actual outcome, not a proxy, score or number of edits. When effectiveness is primary, compare efficiency only after equivalent or improved outcomes; resource use may itself be the intended outcome. Use the minimum process yielding trustworthy evidence. An obvious correction needs one hypothesis, a valid comparison and a short record, not a tournament. No hooks or global configuration required. The bundled supervisor is auto-started for explicit-N and verifiable goal-driven campaigns when the host supports an agent CLI; its benchmark and promotion logic are provider-independent.

### Externally enforced DONE WHEN

Classify each request as **fixed-N** (exactly N evaluated candidates), **goal-driven** (an unmet, independently measurable target without N), or a genuinely **one-off** correction. Goal-driven campaigns use `scripts/auto_start.py launch --until-target`, not a model-controlled loop; the supervisor calls fresh workers until verified `target_completion=MET`. A partial `KEEP`, an early "done" response, or a successful regression suite is not completion. No implicit iteration cap is applied to a measurable goal; user resource budgets and real blockers still apply. The outer agent starts the supervisor without asking the user to invoke another command. See [automatic enforcement](references/auto-enforcement.md).

**Admit only representative benchmarks.** Freeze `case_requirements` and measure `case_facts` in the actual workload. For example, measuring an empty video-feed shell cannot establish how fast a real feed with loaded cards renders. Reject missing content and substituted proxies before optimizing. Prefer public/anonymous alternatives rather than asking for private account access. When coverage differs from the user goal, disclose the narrower scope. See [outcome evaluation](references/evaluation-harness.md).

### Evaluation contract — REQUIRED BEFORE OPTIMIZATION

Before editing, understand the **kind of user-visible improvement**: functionality, performance, maintainability, visual quality, UX, documentation or a combination. An ambiguous request requires inspecting the actual system and identifying a credible user outcome; a category word alone is not an evaluation. Infer a grounded direction when possible; ask one question only when a consequential preference cannot be resolved. **Efficacy precedes efficiency**: do not optimize counts, code size, latency or tokens unless they improve the actual goal or are explicit requirements. Read [outcome evaluation and blind review](references/evaluation-harness.md) for substantial goals. Where shell is available, use `scripts/contract_init.py` to draft, then finalize a concrete frozen `evaluation.json` using observed cases, baseline, hard checks, benchmarks and reviewer criteria. A draft is not acceptance evidence.

For substantial work, freeze the **priority order**, non-negotiable qualities, representative and adverse scenarios, and an explicit **DONE WHEN** contract. Benchmark improvement and task completion are different facts: `KEEP` may coexist with `target_completion=NOT_MET`. Use separate final-target checks or criterion-anchored independent review when the task warrants them; protect those checks from the implementer. A single favorable run or reviewer verdict cannot certify every required scenario. Do not force visual-specific checks or a reviewer on simple deterministic tasks.

For an N-campaign, pass `--evaluation-contract PATH` to the bundled supervisor. A worker's `keep` is only a PROPOSAL: the supervisor owns final promotion after frozen executable checks and, for visual/UX, an independent result-only judge. The judge receives anonymous rendered outcomes, not source or author explanations, and may report TIE/UNCERTAIN. When a judge cannot be started or a result cannot be verified, record HOLD rather than claiming a gain. For visual tasks require actual ingame/rendered evidence and a frozen review contract; do not launch an unaudited visual campaign. Subagents should have a fresh context; note that a source-free prompt does not by itself prevent filesystem access. For implementation or code-quality reviews, use a separate code-aware auditor if code inspection is necessary.

### Automatic enforcement for explicit N or independently checkable target — REQUIRED FIRST ACTION

When the request specifies a fixed number of iterations **or an unmet goal that requires iterative optimization**, and this is the **outer** agent with a supported CLI (`RR_SUPERVISED` is not `1`), do not begin editing the candidate manually. After identifying the Git worktree, the source scope and the frozen outcome evaluator, **invoke the terminal/shell tool yourself** to run the installed skill's `scripts/auto_start.py launch` with the exact user goal, either `--iterations N` or `--until-target`, `--workspace PROJECT_ROOT`, `--artifact SOURCE_PATH`, `--evaluation-contract PATH`, and `--evidence-kind visual` for graphical work (otherwise `generic`). Select `--harness codex|claude|command` based on actual capabilities; a custom `--agent-command` JSON argv connects AGY or another provider where available. Resolve the script relative to this `SKILL.md`; never use a guessed global path or ask the user to run it. Check `python .../scripts/auto_start.py status --state-dir PROJECT_ROOT/.refinement/loop-contract` and inspect `controller.log` as needed; report actual receipts, not the model's opinion. The launcher starts the independent supervisor; the supervisor, not this outer response, drives the remaining trials. An interactive response ending is not campaign completion.

Before launching, save a safe Git checkpoint on an experiment branch. Do not silently commit unrelated user changes or pass `--allow-dirty` without identifying and preserving their ownership. Launch one controller only: if already running, inspect its status instead of starting another. A user-specified wall-time limit is passed as `--max-seconds`; do not invent a campaign deadline. `--turn-timeout` is only a per-worker hang guard. If the CLI is missing, spawning is blocked, the workspace cannot be safely checkpointed, or this host has no supported CLI, **disclose the limitation** and use the local receipt guard for work in the current turn; never say automatic continuation is guaranteed. Never weaken evidence requirements to satisfy the count.

When `RR_SUPERVISED=1`, **do not call `auto_start.py`, do not create another supervisor, and complete only the one verified candidate requested by your controller**. If the user requests a genuinely one-off correction without a fixed count or continuing target, follow the direct workflow below. More detail: [automatic supervisor](references/auto-enforcement.md).

## 1. Establish the contract

Read the request and inspect the artifact in use. Resolve what should improve, for whom/in which conditions, and what must stay. A category (e.g. optimize) may not resolve the goal. If the outcome is open or materially ambiguous, use [discovery](references/discovery.md); skip for a resolved goal or existing contract. State grounded assumptions; ask only when a consequential choice/access remains unresolved. Never invent observations; suggestions do not authorize edits.

Before editing, record in `.refinement/` or existing project records (one file suffices for small work):
- Intent, scope/non-goals, observed gap, excellence anchors and strengths to preserve. Distinguish mandatory behavior from unfinished target quality.
- Primary outcome(s), observable success, meaningful gain, hard requirements, target and referenced trade-off limits (absolute, original, per-step, etc.). Preserve quality; count time/tokens only as intended or secondary. Do not substitute an easier metric.
- Evaluator, case identity, conditions, original outcome and guards. Match evidence to the goal; check that a relevant gain is detected and a misleading apparent gain is rejected where feasible. Include representative/adverse cases and usage states. Freeze acceptance; documented evaluator defects or authorized goal changes require a revised contract and comparable baseline.
- Starting revision, unrelated work, rollback, wall-clock start and user budget. Explicit **N iterations** means N distinct evaluated candidates. For a verified goal, `--until-target` continues until external MET or a real blocker, without a 12-attempt ceiling. Only ordinary non-campaign refinements default to up to 12 attempts. Reserve confirmation/handoff capacity; measure actual elapsed cost.

Baseline = original; incumbent = best accepted at its recorded scope (initially baseline for comparison, not automatically admissible); candidate = unconfirmed trial. Preserve reproducible baseline/incumbent. Simple work needs only this core; load references as needed:
- Ambiguous measures, multiple kinds of improvement or substantial outcome validation: [outcome evidence](references/outcomes.md).
- Substantial evaluation: [shared decisions](references/evaluation.md) plus [quantitative](references/quantitative.md) for metrics/noise/regimes, [qualitative](references/qualitative.md) for judgment/visual quality, or relevant portions of both.
- Improving downstream outcomes of a prompt, workflow or skill: [method evaluation](references/methods.md). Pin the active controller outside editable candidates; judge downstream results, not instruction elegance.

### Explicit iteration contracts (e.g. "30 iterations")

A numerical iteration request is a **binding deliverable**, not a suggestion to try a few alternatives. An A/B comparison does not mean N experiments; count each distinct tested candidate once, never the baseline, no-op edits, repeated tests without a new candidate, untested ideas or text summaries. Set `required=N` and `completed=0` before starting; after every genuine trial record hypothesis, changed artifact identity, actual evidence and keep/discard outcome. Report `completed/N` continuously; an early successful-looking result is an incumbent, not an exemption from the stated count. Use later trials to challenge robustness, explore different mechanisms/conditions or refine quality; never sabotage quality or manufacture trials.

When local shell/Python tools are available, read [iteration contract](references/iteration-contract.md) and use `scripts/loop_guard.py` for an externally inspectable receipt and final count gate (automatically managed by the supervisor if it was launched). The tool refuses credit for unchanged/duplicate artifacts or missing/stale evidence. In a supervised run the worker is permitted **exactly one receipt per invocation**; the controller evaluates that one candidate against the **best accepted incumbent**, independently of its original baseline. Only the controller commits accepted source revisions; rejected work is archived and restored without deleting fresh screenshots outside source scope. A passing test without a measured user-outcome gain or independent qualitative comparison is not sufficient for KEEP. **Check the tool status before ending**: `INCOMPLETE 2/30` must never be described as complete, solved, plateaued or an authorized reduction to two. This requirement outranks the normal early-stop heuristic and default ceiling. Only an explicit user stop/change, an actual resource limit, or a concrete irrecoverable blocker permits an **INCOMPLETE** handoff before N; report exactly why and how many remain. If no meaningful further experiments exist, disclose that blocker—do not fabricate them. A skill alone cannot force another model turn; the automatically launched supervisor can invoke supported fresh agent CLI sessions while access and budgets permit. If the launch tool itself is ignored or blocked, report the limitation rather than claiming enforcement.

## 2. Observe → hypothesize → test → learn

Before each cycle check budget and state; reconcile interrupted/unlogged work or invalid evaluation first.

**Observe and diagnose.** Inspect actual outcome and remaining gap; retrieve specific cases, contrasts, strengths, logs/screenshots, measurements and historical evidence. Separate facts and causal explanations. When causes compete, run a distinguishing test and try to refute the leader. Direct reproduction suffices for obvious issues; see [diagnosis](references/diagnosis.md) for uncertainty.

**Propose.** Target the most consequential remaining evidenced gap or the diagnostic that unlocks it, not an easy metric or cosmetic variation. Choose a coherent testable change. When uncertain, compare distinct mechanisms by evidence, expected benefit, falsifiability, cost, risk and learning value. Record parent, evidence, prediction, falsifier, test, scope and cost before editing. Coordinated changes are allowed when the mechanism requires them. See [exploration](references/exploration.md) for alternatives and selection.

**Implement.** Isolate/snapshot parent; preserve unrelated user work. Apply change and run planned comparison. Never alter acceptance, data or requirements to manufacture success. Untested hypotheses remain unresolved; a verified candidate failure can still violate a guard. Diagnose within budget.

**Evaluate.** Verify actual version, fresh output and comparable conditions. Use two-layer evaluation when relevant: executable measures for correctness/performance, and source-free blind model judgments for visual/UX. The implementing agent never self-certifies a substantial visual gain. Cheap search probes guide selection; do not discard a plausible mechanism solely on an insensitive proxy. Promotion needs representative outcome evidence vs incumbent, independent guards where applicable and the affected end-to-end path. Plan negative/boundary cases early. Don't infer universal gains from favorable groups or invent workload weights. Judge qualitative outcomes from actual output, anchored criteria and localized evidence, not arbitrary scores. A valid deterministic comparison may suffice for simple work. Distinguish noise, prior/new defects, regressions and untested checks.

**Decide.** The worker can propose a keep, but when a supervisor exists only the frozen external promotion gate may approve it. Promote only a valid, meaningful gain over incumbent (or demonstrated equivalence under a declared tie-break), within every frozen requirement and trade-off limit at its reference; don't reset cumulative allowances. Unknown guard defers approval. Confirm borderline gains or label uncertainty. Accept a staged milestone only within its declared scope; partial progress is not target completion. Pre-existing violations still prevent satisfying the requirement. Keep admissible specialist alternatives/evidence, not as global winners. Restore only experiment-owned changes on rejection.

**Learn and continue.** Read the previous external report including `target_completion`, case coverage, severity findings and failed completion checks. Record prediction, realized evidence, separate execution/selection/hypothesis outcomes, uncertainty, cost, lesson and **next experiment**. Update the remaining gap and best verified outcome, not just the latest score. Immediately compare the new result with the target again; an accepted improvement or passing tests do not by themselves finish an open-ended refinement. Keep rejection conditions; reconsider discards only when new evidence invalidates the rationale (not the same as replicating noisy runs). Preserve state and accepted revisions in Git or equivalent snapshots. Use [memory](references/memory.md) for recovery and archives.

## 3. Adapt the search

After about three valid non-improving attempts, recurring symptom or oscillation, recheck diagnosis/evaluator. Invalid trials aren't plateau evidence. Explore a distinct mechanism or parent. Use independent contexts when available and justified; otherwise sequential passes (not independent). Protect incumbent; use equal evaluation conditions and isolate/serialize shared resources.

Combine complementary parents only as a new experiment; test their strengths, interactions and boundaries. For condition-dependent gains compare setup/use costs; test an observable dispatch rule and crossover before promotion. Compare predicted with realized outcome gains/costs periodically; adjust next hypotheses, not acceptance. Recheck which remaining gap matters most and whether the current measurements can detect it. A failed single alternative is not an evidenced plateau.

## 4. Continuation gate — decide whether the **goal**, not a patch, is finished

**After every promotion and before ending**, inspect the best actual result against the original target/reference. State: (1) what is verified better, (2) the most consequential remaining user-visible gap, (3) a plausible distinct next test, and (4) actual budget left. If a material gap remains and a safe, testable next step fits the budget, **run the next observe → hypothesize → test → learn cycle now**. A passing regression suite, one accepted patch, an intermediate milestone, a progress report, or a list of unfinished improvements is not completion. For visual/UX targets, compare the actual rendered experience with the referenced quality, not just colors, counts or code correctness; see [qualitative](references/qualitative.md).

When the user delegates design judgment ("make it look best"), choose and test reversible in-scope improvements without repeatedly asking whether to continue. A request to stop asking questions is not a request to stop refining. Ask only for consequential unresolved preference, scope or access decisions; obey explicit pause/stop/report requests. Do not add unrelated features merely to fill attempts.

**Stop only with an evidenced reason**: for an explicit N-iteration contract, N genuine experiments recorded by the gate, user-requested stop, actual budget exhaustion or a documented blocker (unfinished runs are **INCOMPLETE**). Only when N was **not** explicitly requested may the verified target or evidenced plateau end the loop early. For an open-ended quality gap, plateau requires examining credible alternatives and, when feasible, testing at least two materially different mechanisms since the last meaningful gain. One unsuccessful trial or the absence of a numeric score is not plateau evidence. If the host interrupts execution, record the next exact action rather than claiming the target was reached. Simple fully resolved fixes can still stop after one valid experiment.

## 5. Confirm and deliver

Freeze the best candidate; confirm vs baseline on representative/adverse cases, including unexposed confirmation for adaptive/high-impact searches. Never tune against final confirmation and still call it untouched. If a required check fails or cannot run, preserve the best sufficiently verified version or report narrower scope. Report observed gains, retained strengths, costs, trade-offs/unknowns, evidence, stop reason and exact next action; hand off recoverable state. Claim only observed results; don't promise unsupported unattended execution.
